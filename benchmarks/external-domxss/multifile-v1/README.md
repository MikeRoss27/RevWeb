# External multi-file DOM XSS positive corpus (v1)

Source: [`kanaoka-laboratory/multifile-domxss-dataset`](https://github.com/kanaoka-laboratory/multifile-domxss-dataset)

- Pinned upstream commit: `28f06b4b331c6192477c8987deee3cfaf08eaf57`
- License declared upstream: Apache-2.0; the upstream license is retained in `LICENSE`.
- Upstream README cites Hiura and Kanaoka's DICOMO 2023 dataset proposal; a later 2025 paper also describes the 342-case multi-file evaluation set.
- Corpus: 342 positive project cases in five file-splitting methods; 69 unique source/sink pairs. Repeated split variants are correlated and must not be counted as 342 independent vulnerabilities.
- No negative cases are supplied. This positive-only corpus cannot measure precision, false-positive rate or overall accuracy.
- The examples are generated by rearranging DOM XSS cases from Google Firing Range into ES-module file structures. They are external to Webrev but synthetic and not a collection of real-world bug bounty findings.
- The 342 folders comprise 274 two-module cases and 68 three-module cases. The 69 source/sink templates recur across the split methods, so the variants are correlated. The label is associated with each folder by its source/sink path; the upstream does not provide line-level flow annotations or a machine-readable manifest.

`cases.jsonl` preserves each case's HTML and JavaScript files as a JSON map. It is a normalized export of the pinned upstream tree; source excerpts are not edited. CI now links explicit ES-module value imports between separate file ASTs, matching the current batch extraction pipeline. The source and sink for these cases are in different modules, so this diagnostic measures exact cross-file propagation coverage through the current pipeline; it is not an estimate of intra-file detector recall. The runner reports a subset whose source and sink categories are represented by Webrev's current DOM taint model. The subset is for scope-aware diagnostics, not a claim that out-of-scope cases are safe.

Upstream describes 19 source categories and 34 sink categories. The source mapping is by category: for example, upstream `postMessageEvent.data` (source 15) maps to Webrev's modeled `event.data`; it is not a literal string equivalence. Webrev's current model includes sources `01,02,03,04,05,10,11,12,13,14,15,19` and sinks `09,10,12,15,18`; this mapping was checked against the source/sink declarations in `domsinks.rs`. It yields 25 unique source/sink pairs across 122 correlated split variants. The upstream source/sink labels are used as the positive ground truth; no negative labels are inferred.

## Reproduce

```sh
cargo test -p webrev-extract --test domxss_multifile_external -- --nocapture
sha256sum -c SHA256SUMS
```

The test validates corpus shape and guards the measured 26 exact cross-file matches as a regression count; this is not an accuracy threshold. The positive cases are synthetic and correlated.

## Executed result

On 2026-10-16 UTC, the command above reported 0/122 exact source-to-sink matches
across independently extracted files in the category-compatible subset. The
source and sink are in separate modules, so this is a multi-file propagation
coverage diagnostic, not intra-file detector recall. It reported 12 raw
DOM-flow signals across the full corpus, but none matched the source and sink
named by its case. All five split methods had zero exact matches. See
`results.json` for machine-readable counts. No negative examples are supplied,
so precision and false-positive rate are unavailable.

## Linked-module follow-up (2026-10-17)

The same corpus now yields **26/122** exact modeled matches (13/25 unique
source/sink pairs): type01 13/25, type02 13/22, types03–05 0/25 each. The
runner uses one session per case and resolves explicit imports by module URL;
it never concatenates files. Raw flow signals occur on 44/342 cases, but only
the exact annotated source/sink matches count toward the modeled total.

Candidates remain `Suspicious` with `Medium` confidence and source/sink
provenance. Only straight-line value-export initialization is summarized;
function exports, namespace imports, reexports `from`, and interprocedural
flows remain unsupported. The pipeline analyzes modules already collected;
it does not fetch additional imports. No negative labels or browser replay
have been added, so precision and FPR remain unmeasured. See
`linked-results.json` and `linked-run.log`; `results.json` retains the 0/122
independent-file baseline. The command was executed with
`CARGO_TARGET_DIR=/home/na/.cache/webrev-validation-target`,
`CARGO_PROFILE_DEV_DEBUG=0`, and `CARGO_PROFILE_TEST_DEBUG=0`.

## Direct exported-function calls follow-up (2026-10-17)

The final bounded function-summary pass yields **63/122** exact modeled
matches: type01 13/25, type02 13/22, type03 13/25, type04 13/25, type05 11/25.
Unique modeled source/sink pair coverage stays **13/25**; the additional hits
cover other split variants of those pairs. Raw flow signals occur on 90/342
cases and must not be counted as 90 annotated exact matches. See
`function-results.json` and `function-run.log`; previous artifacts are retained.

Only direct calls to resolved imports of ordinary synchronous function
declarations are summarized: source-returning functions and sinks consuming
parameters. Functions must have straight-line bodies, at most 16 parameters,
64 statements and 32 traces; at most 64 function exports are examined per
module. Uncalled functions and closures do not create module-flow findings.
Mutable module captures, recursive interprocedural analysis, async/generators,
namespace imports and reexports remain unsupported. Literal dead boolean
branches are skipped; opaque conditions are analyzed without resolving their
paths. Runtime reachability and exploitability remain unverified. Results
stay `Suspicious` / `Medium`; the positive-only corpus still cannot measure
precision or FPR. The runner guards63 exact matches as a regression count.
