# Indicative SPA scan after storage indexing

This is an indicative paired scan, not final attribution to the storage index.
The baseline is commit `61b843daf845946060abae026b43349170ff177b`; the candidate
is a dirty shared worktree. During candidate compilation, another shared source
file (`js_regex.rs`) was edited. Its mtime falls inside the candidate build
window, so this archive cannot prove which exact regex source was compiled.
The candidate count (760 findings) also differs from the baseline (574), which
confirms that other behavior changes are included. The fixture is the local
synthetic SPA generated by `harness.py`; it is not OWASP Juice Shop.

The same local 120-page fixture and crawl settings were used. All 40 scans
exited successfully and produced valid reports. Raw observations are in
`results.json`. The reduced regression relative to earlier SPA measurements
cannot be credited to the storage index because the worktree included other
concurrent changes. No isolated before/after storage-index number was measured.

## Reproduction and snapshot hashes

The command was:

```sh
python3 benchmarks/performance/2026-10-16/spa-storage-index/harness.py \
  --baseline-ref 61b843daf845946060abae026b43349170ff177b \
  --runs 20 --pages 120 --profile site \
  --output /tmp/webrev-perf-storage-index
```

The harness builds baseline and candidate separately in release mode, then
alternates 20 local loopback scans per revision. Compilation is excluded from
scan wall time. The run completed at `2026-10-16T22:12:10Z` (UTC).

`source-snapshot.json` records post-run hashes for the relevant source snapshot,
Cargo lock, harness, fixture manifest, and the regex extractor. Since the regex
source changed during the candidate build, these hashes describe the captured
workspace after the run and are not asserted to be the exact compiled input.
`SHA256SUMS` covers the raw JSON, scripts, patch, manifest, and metadata.
